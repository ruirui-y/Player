# 音视频同步完整流程梳理

## 一、核心本质

**音视频同步的本质是：音频按真实时间播放，用它的播放进度作为参考时钟，视频帧的渲染时间向这个时钟对齐，差值超过阈值时通过跳帧或等待来拉回同步。**

核心路线只有两条：

1. **数据流**：文件 → 解封装 → 解码 → 缓冲队列 → 同步判断 → 渲染
2. **时钟流**：音频设备播放位置 → Audio Clock → 与视频 PTS 对比 → 决定渲染时机

---

## 二、FFmpeg 帮你做了什么，没做什么

### FFmpeg 做了（你只需调用 API）
- 打开文件、探测格式（`avformat_open_input`）
- 找到音视频轨道（`avformat_find_stream_info`）
- 从磁盘实时解析出压缩包（`av_read_frame`）
- 解码（`avcodec_send_packet` + `avcodec_receive_frame`）

### FFmpeg 没做（需要你来实现）
- ❌ 内部并没有"AVPacket 队列"——它只有 I/O 读缓冲（一堆原始字节），每次 `av_read_frame` 调用是实时从 I/O 缓冲里解析出一个压缩包给你。**不是你想象中"打开视频时就解出所有 AVPacket 等着你来取"**
- ❌ 不会帮你管理缓冲队列——你要自己建
- ❌ 不会帮你做同步决策
- ❌ 不会帮你渲染画面和播放声音

---

## 三、打开与初始化

```
avformat_open_input()
    ↓
打开文件，建立 I/O 读缓冲（从磁盘读一批原始字节到内存）
    ↓
avformat_find_stream_info()
    ↓
探测出视频流和音频流，拿到各自的 stream_index
    ↓
avcodec_find_decoder() + avcodec_open2()
    ↓
打开视频解码器（H.264）和音频解码器（AAC）
```

此时初始化完毕，还没有数据流动。

## 五、第一步：读取线程

读取线程是**生产者**，循环调用 `av_read_frame()`。

```
每次调用 av_read_frame()：
    ↓
FFmpeg 从内部 I/O 缓冲（原始字节）里现场解析出
下一个完整压缩包的边界
    ↓
填充到你传进去的 AVPacket 结构体中
    ↓
你拿到一个 AVPacket：
    - data[]      → 压缩的 H.264 或 AAC 数据
    - size        → 数据长度
    - stream_index → 标记是视频包还是音频包
    - pts / dts   → 时间戳
    ↓
把这个包复制一份，push 到队列①（AVPacket 队列）
    ↓
如果队列①满了（达到最大缓冲包数），就等待解码线程消耗一些再继续
```

**读取线程没有做任何"压缩"操作**——文件里存的本来就是压缩过的 H.264/AAC，它只是在从磁盘搬运到内存队列。

**一个关键理解**：`av_read_frame` 并不是从某个已经存在的"AVPacket 队列"里取数据，而是实时从 I/O 缓存（原始字节）中解析出来的。

文件读取完后，放一个结束标记（如 `nullptr`）到队列通知解码线程。

---

## 六、第二步：解码线程

解码线程既是**消费者**（消费 AVPacket 队列），又是**生产者**（生产 AVFrame 队列）。

```
从队列①取出一个 AVPacket
    ↓
判断 stream_index：
    ↓
如果是视频流：
    avcodec_send_packet(video_dec, pkt)
    avcodec_receive_frame(video_dec, frame)
        ↓
    得到 AVFrame，里面是原始 YUV 像素
    frame->pts 继承自原始 packet 的 PTS
        ↓
    push 到队列②（视频帧队列）
    ↓
如果是音频流：
    avcodec_send_packet(audio_dec, pkt)
    avcodec_receive_frame(audio_dec, frame)
        ↓
    得到 AVFrame，里面是原始 PCM 采样
        ↓
    push 到队列③（音频帧队列）
```

解码线程不断循环，直到从队列①取出结束标记（`nullptr`）。

**为什么不能先全部解完再播？**
- 内存爆炸：一个 2 小时 4K 视频，全部解成 AVFrame 要几十 GB
- 启动太慢：用户要等全部解码完才能开始看
- 实时性：播放器永远只缓冲未来几秒的数据

---

## 七、第三步：时间戳处理（PTS）

每个 AVFrame 都携带一个 **PTS（显示时间戳）**，表示这一帧应该在什么时刻被显示。

```
FFmpeg 返回的 PTS 的单位（time_base）因音视频流而异：
    视频流的 time_base 可能是 1/90000（H.264 的 90kHz 时钟）
    音频流的 time_base 可能是 1/44100（采样率）
```

必须把音视频的 PTS 统一到同一个基准上才能比较：

```cpp
// 统一转换成微秒
video_pts_us = av_rescale_q(video_frame->pts, video_time_base, AV_TIME_BASE_Q);
audio_pts_us = av_rescale_q(audio_frame->pts, audio_time_base, AV_TIME_BASE_Q);
```

## 八、第四步：主时钟（Master Clock）的选择

音视频同步必须有一个参考时钟，其他轨道向它对齐。

### 三种策略

| 策略                      | 做法                               | 优缺点                                   |
| ------------------------- | ---------------------------------- | ---------------------------------------- |
| **音频为主时钟** ✅ 最常用 | 音频按真实时间播放，视频向音频对齐 | 人耳对声音断续最敏感，画面跳一帧不易察觉 |
| 视频为主时钟              | 视频按真实时间渲染，音频向视频对齐 | 声音容易断续，体验差                     |
| 外部时钟（系统时间）      | 双方都参考系统时钟                 | 可用于推流同步，但设备间时钟可能漂移     |

### 行业标准：音频为主时钟

Audio Clock 的计算方式：

```
audio_clock = 音频设备已播放的采样总数 / 采样率

举例：
    采样率 44100，已经向音频设备写了 441000 个采样
    audio_clock = 441000 / 44100 = 10.0 秒
```

每次音频设备回调时更新这个值。

---

## 九、第五步：同步判断（渲染线程的核心）

渲染线程负责三件事：
1. 更新 Audio Clock
2. 对比视频帧的 PTS 与 Audio Clock
3. 决定渲染时机

### 同步逻辑

```
每 ~10ms 检查一次：

渲染线程取出队列②队首的视频帧
    ↓
拿到该帧的 video_pts（已转为秒）
    ↓
获取当前 audio_clock（音频播放位置，单位：秒）
    ↓
计算差值：diff = video_pts - audio_clock
    ↓
```

| diff 值                 | 含义                             | 动作                               |
| ----------------------- | -------------------------------- | ---------------------------------- |
| `diff > +40ms`          | 视频比音频快 40ms 以上（未来帧） | **跳帧**：丢弃当前帧，直接看下一帧 |
| `diff 在 +20ms ~ +40ms` | 视频稍微超前                     | **立即渲染**，不等                 |
| `diff 在 ±20ms`         | 基本同步                         | **正常渲染**                       |
| `diff < -40ms`          | 视频已经过时 40ms 以上           | **等待**：重复上一帧，等下一帧到来 |

### 音频渲染

音频没有复杂的同步逻辑——它本身就是参考时钟。直接从队列③取出音频帧写入音频设备的缓冲区即可。

---

## 十、第六步：渲染输出

- **视频渲染**：把 AVFrame 的 YUV 数据送 GPU/SDL/Qt 显示
- **音频输出**：把 AVFrame 的 PCM 采样写入音频设备的环形缓冲区

---

## 十一、全流程一句话总结

> **读取线程不停从磁盘读压缩包（AVPacket）放进队列①，解码线程从队列①取出压缩包解码成原始帧（AVFrame），视频丢进队列②、音频丢进队列③，渲染线程用音频实际播放位置作为参考时钟，对比视频帧的 PTS，差值超过阈值时通过跳帧或等待来保持同步。**

## 十二、常见误区速查
