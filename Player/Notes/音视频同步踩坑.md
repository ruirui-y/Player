## 踩坑记录：音视频同步流水线改造

### 坑 1：Play 启动顺序错误

**错误表现：**
- DecodeLoop 还没启动，Reader 和 Decoder 就先跑了
- audio_queue_ 堆到 469 帧，video_queue_ 堆满（GPU DPB 20 帧上限）
- DecodeLoop 启动后，PTS 从 350ms 直接跳到 11000ms

**错误代码：**
```cpp
void Play()
{
    reader_.Start();          // ① 生产者先跑
    decoder_.Start();         // ② 生产者先跑
    audio_renderer_->Start();
    decode_thread_ = std::thread(&DecodeLoop, this);  // ③ 消费者后跑
}
```

**正确做法：**
```cpp
void Play()
{
    audio_renderer_->Start();
    decode_thread_ = std::thread(&DecodeLoop, this);  // ① 消费者先启动
    reader_.Start();          // ② 生产者后启动
    decoder_.Start();
}
```

**原理：** 消费者先就位，生产者再开始生产，队列不会提前堆积。

### 坑 2：GPU 硬解 DPB 限制导致流水线卡死

**错误表现：**

- video_queue_ 始终卡在 19~20 帧不再增长
- 不是 SafeQueue 有上限，是 GPU 解码器内部的 DPB（解码图片缓冲区）只能装约 20 帧
- `avcodec_receive_frame` 返回 EAGAIN，新帧出不来

**错误推理：**

- 以为是 SafeQueue 加了上限
- 误导了排查方向，浪费了大量时间

**正确理解：**

- H.264 硬解时 GPU 内部有 DPB，容量有限（通常 ~16~20 帧）
- 一个视频帧被 Push 到 video_queue_ 后，它占着的 GPU DPB 槽位**不会被释放**，必须等到这一帧被 `av_frame_free` 之后，DPB 对应的槽位才会腾出来
- DPB 满了 → receive_frame 返回 EAGAIN → DecodeVideoPacket 的 while 循环 break → 不产出新帧——也就是说，video_queue_ 里卡的 20 帧的 GPU 内存全没释放，DPB 槽位被这些帧占满，新帧出不来
- 只有 DecodeLoop 先 Pop 出来，再 Render，再 av_frame_free → GPU 内存释放 → DPB 槽位腾出 → 下一帧才能产出
- 而 Pop + Render + av_frame_free 这个链条必须在一个循环里走完，中间不能阻塞（比如 sleep 等 PTS），否则 Pop 出来的帧在手里拿着不 free，DPB 照样占着，还是卡死
- **所以 DecodeLoop 绝对不能阻塞等待 PTS**，必须尽快完成 取帧→渲染→释放 的全流程，让 GPU DPB 一直有空位

### 坑 3：PTS 等待阻塞在渲染线程

**错误做法：**
```cpp
if (wait_ms > 0)
    std::this_thread::sleep_for(std::chrono::milliseconds(wait_ms));
```

**问题：** sleep 期间 DecodeLoop 不 Pop video_queue_ → video_queue_ 被消费者卡住 → GPU DPB 满 → 新视频帧不产出 → 卡死。

**正确做法：**
- DecodeLoop 的职责是**尽快消费所有队列**，越快越好
- 帧到了时间才渲染，没到时间就存起来
- 用一个本地 render_queue（deque）做缓冲

```
DecodeLoop 循环：
    ① while TryPop video_queue_ → 全部取出，存到本地 render_queue
    ② while TryPop audio_queue_ → 全部取出，喂给 AudioRenderer
    ③ 检查 render_queue 队首的 PTS → 到时间就渲染
    ④ 如果本地队列空了 → 睡 1ms 避免空转
```

### 坑 4：同步方案的演变与误区

**方案一（错误）：音频时钟 diff 同步**
```
diff = video_pts - audio_clock
if diff > 40 → sleep
if diff < -40 → 跳帧
```
- 依赖 audio_queue_ 限流，但没加
- 音频时钟可能为负（processedUSecs 问题）
- 队列堆积后 diff 爆炸，全在跳帧

**方案二（错误）：PTS 直等**
```
elapsed = now - start_time
wait_ms = pts_ms - elapsed
if wait_ms > 0 → sleep
```
- 理论正确，但在 GPU 硬解场景下致命
- sleep 导致不 Pop → DPB 满 → 流水线卡死

**方案三（正确）：本地渲染缓冲 + 立即消费**
```
while TryPop(video_queue_) → 全取出，存到 render_queue
while TryPop(audio_queue_) → 全取出，喂给 AudioRenderer
检查 render_queue 队首帧：
    if PTS ≤ 当前时间 → 渲染并弹出
    if render_queue 为空 → sleep(1ms) 避免空转
```

### 坑 5：错误归因浪费大量时间

在整个排查过程中，我犯了一系列错误推理：

| 错误推理                 | 实际情况                                              |
| ------------------------ | ----------------------------------------------------- |
| GPU 异步解码导致顺序乱   | 代码是同步阻塞的（while receive_frame），没有异步问题 |
| Decoder 偏袒音频忽略视频 | Decoder 严格串行，取一个解一个，没有偏好              |
| SafeQueue 有上限         | SafeQueue 没有设置 max_size，卡 20 是 GPU DPB 限制    |
| 首帧 PTS 跳变是队列乱序  | 是 Play 顺序错误导致，先启动生产者后启动消费者        |

**教训：** 出问题时先加日志看数据，不要猜。Decoder 每一行都打印包类型、PTS、队列大小，3 行日志就能定位问题。

### 坑 6：CPU 解码 vs GPU 解码的关键差异 —— 必须换方案

**CPU 软解：**
- 解码慢（一帧 10~30ms）
- 解码器内部没有缓冲区限制
- 可以用 "PTS → sleep" 节奏同步，因为 sleep 时 CPU 解不完下一帧，自然限速

**GPU 硬解：**
- 解码快（一帧 1~3ms）
- 解码器内部有 DPB 限制（~20 帧）
- 不能 sleep 等 PTS → 必须本地缓冲 + 立即消费

**如果你之后遇到"方案换了一个又一个人家都说不对"——先确认你是硬解还是软解。两种模式用不同的同步方案。**

### 正确的同步方案（最终版）

```
DecodeLoop:
    ① TryPop audio_queue_ → 全部喂给 AudioRenderer
    ② TryPop video_queue_ → 全部存入本地 render_queue（deque<pair<AVFrame*, pts_ms>>）
    ③ 检查 render_queue 队首：
           if 队首.PTS <= 当前已过时间 + 16ms (1帧容差)
                渲染并弹出队首
           否则 → 跳过
    ④ if render_queue 空了 → sleep(1ms)
    ⑤ 回到 ①
```

**核心原则：所有 Pop 用 TryPop 而不是阻塞 Pop，DecodeLoop 永远不停。**
