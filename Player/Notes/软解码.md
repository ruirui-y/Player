# FFmpeg TCP 播放器 — 踩坑总结与当前版本说明

## 当前版本为什么能跑通

### 核心修复一：硬件解码的像素格式用对了

之前我一直在用 `AV_PIX_FMT_D3D11VA`（枚举值 172）去做格式协商和判断。但你下载的 BtbN FFmpeg 版本**没有这个枚举值**，因为在 FFmpeg 7.x/8.x 里，它被统一成了 `AV_PIX_FMT_D3D11`（枚举值 170）。

所以当时解码器协商格式时：
- get_format 回调里写的是 `if (*p == 172)` → 永远匹配不上
- 解码器自动降级成了 `DXVA2_VLD`（171）
- 而 Render 函数里判断的是 `if (fmt == 172 && swapchain_)` → 也永远走不进去
- 最后落到软解分支，但 `sws_scale` 不认识 GPU 上的 DXVA2 格式，`sws_getContext` 返回 null → 画面出不来

**现在的做法：** get_format 回调里改成了写 `AV_PIX_FMT_D3D11`（170），同时 Render 函数里判断三个格式（170/171/172），不管解码器最终选了哪个，都能正常处理。

### 核心修复二：统一走"下载到 CPU → 软解"路线

之前我的思路是"硬解帧直接 CopyResource + Present 到屏幕"，但这个方案要求解码器和渲染器共用同一个 D3D11 设备、帧格式必须是 D3D11 texture、还需要正确的 texture subresource 索引。

实际情况是：
- 即使解码器用了 D3D11VA 硬解，FFmpeg 内部也可能用 DXVA2 路径输出
- 直接 `CopyResource` 要求源和目标纹理格式完全匹配，NV12（解码器输出）和 B8G8R8A8（交换链）不能直接 Copy

**现在的做法：** 不管解码器输出什么格式的硬解帧，统一用 `av_hwframe_transfer_data` 把 GPU 上的帧下载到 CPU 内存，再交给 `sws_scale` 转成 RGB。这条路径虽然慢一截（4K 会卡），但**稳**，所有硬件格式都能处理。

### 核心修复三：CreateSwapChain 里正确获取 DeviceContext

之前的 CreateSwapChain 里：
```cpp
d3d11_ctx_ = nullptr;  // 不需要自己的设备上下文
```

但 RenderHardware 里的 `CopyResource` / `CopySubresourceRegion` 都需要 `ID3D11DeviceContext` 来执行。之前没拿 Context，RenderHardware 里检测到 `!d3d11_ctx_` 就直接 return 了，硬解渲染分支走不通。

**现在的做法：** 通过 `device->GetImmediateContext(&d3d11_ctx_)` 正确获取设备上下文。不过当前 RenderHardware 实际上没被走到，因为统一走了"下载到 CPU"的混合路线。但把 Context 补全后，为以后真正的 GPU 直渲染铺好了路。

### 核心修复四：帧率控制

之前的解码线程是"能跑多快跑多快"，4K 视频每秒可能解出上百帧，sws_scale 的 RGB 转换把 CPU 吃满，Qt 主线程的事件队列被 QImage 信号塞爆，界面卡死。

**现在的做法：** 每帧解码后计算耗时，如果不到 33ms（约 30fps），就 sleep 补齐。这样 CPU 占用降下来，主线程有空处理事件，画面就能正常显示了。

## 踩坑回顾

### 坑一：FFmpeg 版本不同，枚举值不同

同一个 `AV_PIX_FMT_D3D11VA`，在 gyan.dev 的包里和 BtbN 的包里定义不一样。踩了一整天，最后发现直接用 FFmpeg 头文件里定义的宏名（`AV_PIX_FMT_D3D11`）比手写数字（172）靠谱。头文件里没定义的枚举值，直接 `#define` 会导致 `pixfmt.h` 解析出错。

### 坑二：`d3d11.h` 和 Qt 头文件的包含顺序

当时头文件里同时包含了 `<d3d11.h>` 和 Qt 的头文件。Windows Kits 里的 `d3d11.h` 定义了 `operator==` 和 `operator!=`，跟 Qt 模板里的 `operator==` 冲突。编译时疯狂报 `error C2733`。

**最终解法：** 头文件里不包含 `d3d11.h`，全部用 `void*` 不透明指针。只在 .cpp 里包含。后来另一个 AI 重构时在 VideoRenderer.h 里直接包含了 `d3d11.h`，但那是专门为渲染器做的，解码器那头仍然用 `void*`。

### 坑三：自己手写 D3D11VA 结构体去对接 FFmpeg

之前我自己定义了 `D3D11VAContextLocal` 和 `D3D11VAFrameLocal` 两个结构体，试图手动匹配 FFmpeg 内部的数据布局。但实际上 FFmpeg 7.x/8.x 的 `AVD3D11VADeviceContext` 比我们想的复杂（有 lock、有引用计数），结构体对不上。

**最终解法：** 放弃手写结构体。用 `av_hwdevice_ctx_create` 让 FFmpeg 自己创建硬件设备，解码器内部怎么组织数据，让 FFmpeg 自己去管。我只需要通过 `av_hwframe_transfer_data` 把帧从 GPU 取出来就行。

### 坑四：MainWindow 的 Qt 属性覆盖了 QLabel 渲染

之前在 MainWindow 构造函数里加了：
```cpp
setAttribute(Qt::WA_NativeWindow, true);
setAttribute(Qt::WA_PaintOnScreen, true);
setAttribute(Qt::WA_OpaquePaintEvent, true);
setAttribute(Qt::WA_NoSystemBackground, true);
```

这四个属性告诉 Qt："这个窗口我自己画，你别管"。结果 `QPixmap::fromImage(image)` 画上去的内容被覆盖了，画面出不来。

**最终解法：** 全部删掉。既然走 QLabel 软渲染，就让 Qt 管理渲染流程。

### 坑五：MainWindow 里 QLabel 初始隐藏

新版本加了 `video_label_->hide()` 和 `OnFrameReady` 里 `video_label_->show()`。如果不 hide，窗口刚启动时 QLabel 是空的，会显示一个白色方块一闪而过。hide 掉等第一帧来了再 show，启动画面干净。

### 坑六：4K 图片用 SmoothTransformation 卡死

```cpp
pixmap.scaled(size(), Qt::KeepAspectRatio, Qt::SmoothTransformation)
```

`SmoothTransformation` 是双线性插值，对 4K 图片做缩放时，CPU 要算几百万个像素的插值，一次就要几十毫秒。主线程被卡住，事件循环阻塞，画面卡死。

**最终解法：** 改成 `Qt::FastTransformation`，不做插值，直接近邻采样。虽然画质稍差，但不卡。

## 当前架构总结

```
main.cpp
  └─ FFmpegPlayer ─── FFmpegDecoder（打开文件、解码）
       │                  │
       │                  └─ av_hwframe_transfer_data（GPU→CPU 下载）
       │
       └─ VideoRenderer（D3D11 交换链 + sws_scale 软解）
              │
              └─ QImage → emit SigFrameReady → MainWindow::OnFrameReady（QLabel 显示）
```

**播放流程：**
1. FFmpegPlayer::OpenFile → FFmpegDecoder 硬解打开（如果支持）
2. 从解码器取出 D3D11 设备 → 传给 VideoRenderer 创建交换链
3. FFmpegPlayer::Play → 启动解码线程
4. 每解码一帧 → VideoRenderer 检测到是硬解帧 → av_hwframe_transfer_data 下载到 CPU → sws_scale 转 RGB → QImage → 信号到主线程 → QLabel 显示
5. 帧率控制在 ~30fps，避免 CPU 满载

**目前是"混合管线"：解码是 GPU 硬解，渲染是 CPU 软解。** 8K 跑不动，4K 勉强能看，1080p 流畅。如果要全 GPU 管线，需要写 HLSL shader 把 NV12 转 RGB 这一步也从 GPU 做。但那属于"第二步"的完全体硬解方案，现在是第一步的通路验证阶段的收尾。
