# 第四阶段笔记：音频串流实现（WASAPI 采集 → Opus 编码 → UDP 传输 → WASAPI 播放）

> 本阶段目标：将服务端系统音频通过 WASAPI 环回采集 → Opus 编码 → UDP 传输 → 客户端解码 → WASAPI 播放，实现端到端音频串流。
> 验收方式：服务端播放任意音频，客户端能实时听到，延迟 < 100ms，无杂音。

---

## 模块一：WASAPI 环回采集 (WasapiCapture)

### 为什么用 WASAPI Loopback

串流系统音频有三种方案：

| 方案 | 原理 | 优点 | 缺点 |
|------|------|------|------|
| 立体声混音 (Stereo Mix) | 声卡驱动提供的混音回录 | 简单 | 很多设备没有此功能，格式不可控 |
| 虚拟声卡 | 安装虚拟音频设备 | 可控 | 需要额外安装驱动，用户体验差 |
| WASAPI Loopback | 共享模式下捕获渲染端点 | 零安装、低延迟、格式可控 | 需要处理设备格式转换 |

WASAPI Loopback 是 Windows 推荐的系统音频捕获方案，不需要额外驱动，且与共享模式音频引擎共用同一条路径，延迟最低。

### 类接口

```cpp
class WasapiCapture
{
    bool Init(uint32_t output_sample_rate = 48000, uint32_t channels = 2);
    void SetCallback(AudioCallback cb);     // PCM 数据回调
    void Start();                           // 启动采集线程
    void Stop();                            // 停止采集线程

    // 回调签名：pcm_data 是交错排列的 int16，已重采样到 output_sample_rate
    using AudioCallback = std::function<void(const int16_t* pcm_data,
                                             int sample_count,
                                             uint32_t timestamp_ms)>;
};
```

### 初始化流程（十步）

```
Init:
  1. CoInitializeEx(MTA)                    // COM 多线程公寓
  2. CoCreateInstance(MMDeviceEnumerator)   // 设备枚举器
  3. GetDefaultAudioEndpoint(eRender, eConsole)  // 默认扬声器
  4. device->Activate(IAudioClient)         // 激活音频客户端
  5. audio_client->GetMixFormat(&pwfex_)    // 获取设备混音格式（必须用 mix format）
  6. audio_client->Initialize(SHARED, LOOPBACK, ...)  // 环回模式初始化
  7. audio_client->GetService(IAudioCaptureClient)    // 获取采集客户端
  8. audio_client->Start()                  // 启动采集
  9. 辅助渲染流（见下方坑 1）                // 保持音频引擎活跃
  10. swr_alloc_set_opts2 + swr_init        // 创建重采样器
```

### 采集线程主循环

```
CaptureLoop:
  CoInitializeEx(MTA)                       // 采集线程也要初始化 COM

  while running:
    1. GetNextPacketSize(&packet_length)    // 查询缓冲区是否有数据
       packet_length == 0 → Sleep(1) 继续

    2. while packet_length != 0:
       a. GetBuffer(&data, &num_frames, &flags)
          flags & SILENT → ReleaseBuffer 跳过

       b. swr_convert(swr_ctx, dst, max_out, src, num_frames)
          float32 @ device_rate → int16 @ 48000Hz

       c. callback_(pcm_buffer, out_samples, timestamp_ms)
          → 投递给 StreamServer::OnAudioData

       d. ReleaseBuffer(num_frames)
       e. GetNextPacketSize(&packet_length)  // 取下一个包
```

### 关键设计：辅助渲染流

```
// WASAPI loopback 的陷阱：如果没有渲染流在播放，GetNextPacketSize 永远返回 0
// 自己开一个静音渲染流，让音频引擎持续运行，loopback 就能收到数据包
hr = device_->Activate(__uuidof(IAudioClient), ...);
render_client_->Initialize(SHARED, 0, ...);   // 注意：不加 LOOPBACK
render_client_->Start();                       // 启动空渲染流
```

**为什么需要**：WASAPI loopback 依赖音频引擎的混音输出。当系统没有声音播放时，音频引擎处于空闲状态，loopback 的 `GetNextPacketSize` 返回 0，采集线程会一直空转。开一个静音渲染流（不写入任何数据）让音频引擎保持活跃，loopback 就能持续收到数据包（静音包），确保采集线程不会卡死。

### 关键设计：SwrContext 重采样

WASAPI loopback 返回的格式是设备的混音格式（`GetMixFormat`），通常是 `float32 @ 48000Hz`，但也可能是 44100Hz 或其他采样率。Opus 编码器只支持 8/12/16/24/48kHz，所以必须重采样。

```
// 源格式：float32 @ device_sample_rate_（WASAPI 返回的混音格式）
// 目标格式：int16 @ 48000Hz（Opus 编码器需要）
swr_alloc_set_opts2(&swr_ctx_,
    &dst_layout, AV_SAMPLE_FMT_S16, output_sample_rate_,
    &src_layout, AV_SAMPLE_FMT_FLT, device_sample_rate_,
    0, nullptr);
```

## 模块二：Opus 音频编码器 (OpusAudioEncoder)

### 为什么用 Opus

| 编解码器 | 延迟 | 码率范围 | 适用场景 |
|----------|------|----------|----------|
| AAC-LC | ~50ms+ | 16~512kbps | 流媒体、存储（延迟高） |
| MP3 | ~100ms+ | 32~320kbps | 存储（延迟太高） |
| Opus | 2.5~60ms | 6~510kbps | 实时通信、游戏串流 |
| PCM | 0 | 1536kbps(48k/16bit/2ch) | 无压缩（码率太高） |

Opus 是专门为实时通信设计的编解码器，Moonlight 官方也使用 Opus。20ms 帧延迟 + 128kbps 码率，音质接近透明，CPU 开销极低。

### 类接口

```cpp
class OpusAudioEncoder
{
    bool Init(uint32_t sample_rate = 48000, uint32_t channels = 2,
              uint32_t bitrate_bps = 128000, uint32_t frame_ms = 20);
    int Encode(const int16_t* pcm_data, int sample_count_per_channel,
               std::vector<uint8_t>& output);    // 返回编码字节数
    int FrameSamples() const { return frame_samples_; }   // 960
    uint32_t FrameMs() const { return frame_ms_; }        // 20
};
```

### 编码参数选择

```cpp
opus_encoder_create(sample_rate, channels, OPUS_APPLICATION_AUDIO, &error);

opus_encoder_ctl(encoder_, OPUS_SET_BITRATE(128000));     // 128kbps
opus_encoder_ctl(encoder_, OPUS_SET_COMPLEXITY(10));      // 最高质量
opus_encoder_ctl(encoder_, OPUS_SET_DTX(0));              // 禁用静音压缩
opus_encoder_ctl(encoder_, OPUS_SET_INBAND_FEC(0));       // 禁用带内 FEC
```

| 参数 | 值 | 原因 |
|------|-----|------|
| Application | AUDIO | 通用音频，不是纯语音（VOIP） |
| Bitrate | 128kbps | 立体声音乐透明音质，局域网带宽充裕 |
| Complexity | 10 | 最高质量，CPU 开销可忽略 |
| DTX | 0（禁用） | 保证连续音频流，避免静音时编码器输出空帧 |
| FEC | 0（禁用） | UDP 丢包由丢帧处理，不需要额外纠错开销 |
| Frame | 20ms (960 samples) | 平衡延迟与编码效率 |

### 帧大小计算

```
frame_samples_ = sample_rate × frame_ms / 1000
               = 48000 × 20 / 1000
               = 960                        // 每声道 960 个采样

frame_total = frame_samples_ × channels
            = 960 × 2
            = 1920                          // 一帧 PCM 总采样数（交错排列）
```

## 模块三：UDP 音频发送器 (AudioSender)

### 设计

```cpp
class AudioSender
{
    bool Init(const char* dest_ip, uint16_t dest_port);
    void SendFrame(const uint8_t* frame_data, int frame_size,
                   uint16_t frame_index, uint32_t timestamp);
    void Close();
};
```

### 关键实现

```
Init:
  1. WSAStartup(MAKEWORD(2,2))
  2. socket(AF_INET, SOCK_DGRAM, IPPROTO_UDP)
  3. inet_pton 填充 dest_addr_
  4. setsockopt SO_SNDBUF = 1MB              // 音频包小，1MB 足够

SendFrame:
  1. FragmentFrame(frame_data, frame_size, frame_index, timestamp, false)
     // 复用 NalUnit.h 的分片逻辑，is_keyframe = false（音频没有关键帧）
  2. for each packet: sendto()
```

### 与 VideoSender 的对比

| 对比项 | VideoSender | AudioSender |
|--------|-------------|-------------|
| 发送缓冲区 | 4MB | 1MB |
| 分片大小 | 1400 字节 | 1400 字节（复用 NalUnit.h） |
| 典型帧大小 | 10KB~200KB（H.264） | 80~400 字节（Opus） |
| 典型分片数 | 7~140 个 | 1 个（单包送达） |
| 端口 | 47998 | 47997 |

**为什么复用 NalUnit.h 而不单独写音频分片**：
Opus 帧通常 80~400 字节，远小于 1400 字节的 MTU 限制，`FragmentFrame` 会将其包装成单个 UDP 包（SOF + EOF 同时设置）。虽然多了一个 9 字节的 NalPacketHeader 开销，但换来了代码统一——接收端可以直接复用 `NalReassembler` 组帧，不需要额外维护一套音频组帧逻辑。

## 模块四：UDP 音频接收器 (AudioReceiver)

### 设计

```cpp
class AudioReceiver
{
    bool Init(uint16_t listen_port, SafeQueue<AVPacket*>* packet_queue);
    void Start();                           // 启动接收线程
    void Stop();                            // 停止接收线程
};
```

### 接收线程主循环

```
ReceiveLoop:
  recv_buf[2048]

  while running:
    1. recvfrom(sock, recv_buf)             // 阻塞等待
       返回 ≤ 0 → 退出

    2. reassembler_.AddPacket(recv_buf, recv_len)
       返回 false → 还没收齐，继续等

    3. frame_data = reassembler_.TakeFrame()

    4. 包装成 AVPacket：
       pkt = av_packet_alloc()
       av_new_packet(pkt, frame_data.size())
       memcpy(pkt->data, frame_data.data(), size)

       // PTS：毫秒时间戳 → 48kHz 时基
       // 48000 / 1000 = 48，所以毫秒值 × 48 = 48000 时基的 PTS
       pkt->pts = timestamp × 48
       pkt->dts = pkt->pts

    5. packet_queue_->Push(pkt)             // 推入队列给 AudioDecoder
```

### PTS 为什么乘 48

Opus 解码器内部使用 48kHz 时基（48000 ticks/秒）。服务端 timestamp 单位是毫秒，乘以 48 就转换为 48kHz 时基下的 ticks：`48000 / 1000 = 48`。这与视频的 PTS 乘 90（90kHz 时基）是同样的思路，只是音频用 48kHz。

### 与 VideoReceiver 的对比

| 对比项 | VideoReceiver | AudioReceiver |
|--------|---------------|---------------|
| 端口 | 47998 | 47997 |
| 缓冲区 | 1MB | 1MB |
| 组帧器 | NalReassembler | NalReassembler（复用） |
| PTS 时基 | 90kHz（×90） | 48kHz（×48） |
| 关键帧标记 | 有（AV_PKT_FLAG_KEY） | 无 |

### 端口复用（SO_REUSEADDR）

```cpp
int reuse = 1;
setsockopt(sock_, SOL_SOCKET, SO_REUSEADDR, (const char*)&reuse, sizeof(reuse));
```

客户端重启时，旧 socket 可能处于 TIME_WAIT 状态未完全释放。不加 `SO_REUSEADDR` 会导致 `bind()` 失败（WSAError 10048），表现为"第一次能连，重启后报错"。

## 模块五：串流音频渲染器 (StreamAudioRenderer)

### 为什么不用 QAudioOutput

| 问题 | QAudioOutput | WASAPI 直接渲染 |
|------|-------------|----------------|
| Debug 模式 | 正常工作 | 正常工作 |
| Release 模式 | 设备枚举失败（"using null output device"） | 正常工作 |
| 缓冲区控制 | 无法精确控制 | GetCurrentPadding 精确查询 |
| 延迟 | 受 Qt 事件循环影响 | 直接写硬件缓冲区 |

**根因**：Qt 5.14 的 QAudioOutput 在 Release 模式下依赖 Windows MMDevice API 枚举设备，某些构建配置下 COM 初始化时机导致枚举返回空列表。直接用 WASAPI 的 `IAudioRenderClient` 绕过了 Qt 的设备管理层，COM 对象在子线程中创建，时序可控。

### 类接口

```cpp
class StreamAudioRenderer : public QObject
{
    void Start();                                               // 打开 WASAPI + 创建 swr
    void Stop();                                                // 停止 WASAPI
    void Close();                                               // 关闭释放

    bool CanAcceptFrame() const;                                // 缓冲区能否接受一帧？
    bool FeedFrame(AVFrame* frame);                             // 接收解码帧 → swr → WASAPI

    void SetVolume(double volume);                              // 0.0 ~ 1.0（软件音量）
    double GetVolume() const;
};
```

### 初始化流程（十步）

```
Start:
  1. swr_alloc_set_opts2(FLTP → S16 @ 48000Hz)    // 重采样上下文
  2. CoCreateInstance(MMDeviceEnumerator)           // 设备枚举器
  3. GetDefaultAudioEndpoint(eRender, eConsole)     // 默认扬声器
  4. device->Activate(IAudioClient)                 // 激活音频客户端
  5. 构造 WAVEFORMATEX（16-bit PCM 立体声 48kHz）
  6. audio_client->Initialize(SHARED, 0, 40ms, ...) // 共享模式，40ms 缓冲区
  7. audio_client->GetBufferSize(&buffer_frames_)   // 获取硬件缓冲区大小
  8. audio_client->GetService(IAudioRenderClient)   // 获取渲染客户端
  9. audio_client->Start()                          // 启动播放
  10. 预填充静音到整个缓冲区                         // 防止启动瞬间杂音
```

### WASAPI 共享模式渲染原理

```
WASAPI 共享模式缓冲区（环形缓冲区）：

  buffer_frames_ = 1920 帧 (40ms @ 48kHz)
  ┌─────────────────────────────────────────────┐
  │ 已播放 (padding)  │  空闲 (free)             │
  └─────────────────────────────────────────────┘
  ↑                   ↑
  播放指针            写入指针

GetCurrentPadding(&padding)   → 获取已填充帧数
free_frames = buffer_frames_ - padding
GetBuffer(free_frames, &buf)  → 获取写入指针
memcpy(buf, pcm_data, ...)    → 写入 PCM 数据
ReleaseBuffer(frames_written) → 提交写入
```

### 40ms 缓冲区的设计依据

```
Opus 帧时长 = 20ms = 960 samples/channel
WASAPI 缓冲区 = 40ms = 1920 frames

  40ms ÷ 20ms = 2 帧

缓冲区至少能容纳 2 帧 Opus 解码后的 PCM 数据。
如果缓冲区太小（如默认 10ms），一帧 20ms 的 Opus 数据放不进去，
会导致 buffer underflow → 播放未初始化数据 → 刺耳杂音。
```

### FeedFrame 写入流程

```
FeedFrame(AVFrame* frame):
  1. 首帧计算 frame_bytes_（缓存，后续复用）
     dst_nb_samples = av_rescale_rnd(swr_delay + nb_samples, 48000, sample_rate, UP)
     frame_bytes_ = av_samples_get_buffer_size(nullptr, 2, dst_nb_samples, S16, 1)

  2. swr_convert(FLTP → S16)
     输入：frame->data（float32-planar，Opus 解码器输出）
     输出：pcm_data（int16 交错排列，WASAPI 需要）

  3. 软件音量缩放（volume_ < 0.99 时）
     samples[i] = samples[i] × volume_

  4. 查询缓冲区空闲空间
     GetCurrentPadding(&padding)
     free_frames = buffer_frames_ - padding

  5. GetBuffer + memcpy + ReleaseBuffer
     frames_to_write = min(sample_count, free_frames)
     GetBuffer(frames_to_write, &buffer)
     memcpy(buffer, pcm_data, bytes)
     ReleaseBuffer(frames_to_write, 0)
```

### CanAcceptFrame 首帧处理

```cpp
bool CanAcceptFrame() const
{
    // ...
    // 首帧前 frame_bytes_ 为 0，此时不检查帧大小，WASAPI 缓冲区有空间就接受
    if (frame_bytes_ == 0)
        return free_bytes > 0;
    return free_bytes >= (UINT32)frame_bytes_;
}
```

**为什么需要特殊处理**：`frame_bytes_` 在 `FeedFrame` 首次调用时才计算。如果 `CanAcceptFrame` 在首帧前用 `frame_bytes_ == 0` 做比较，`free_bytes >= 0` 永远为 true，会导致空帧被"接受"但 `FeedFrame` 实际写不进去。特殊处理让首帧只要缓冲区有空间就接受，后续帧才按实际大小检查。

### 预填充静音

```cpp
// 防止启动瞬间缓冲区为空，声卡播放残留数据导致刺耳噪声
GetBuffer(free_frames, &sil_buf);
std::memset(sil_buf, 0, free_frames * channels_ * sizeof(int16_t));
ReleaseBuffer(free_frames, 0);
```

WASAPI 启动后缓冲区是空的，声卡会立刻开始消费。如果不预填充静音，声卡会播放缓冲区中残留的随机数据（上一次播放的尾巴或未初始化内存），产生刺耳的爆音。预填充零值让声卡先安静地播放静音，等真正的 PCM 数据写入后才出声。

## 模块六：StreamServer 音频集成

### 新增成员

```cpp
class StreamServer
{
    // ---- 第四阶段：音频组件 ----
    WasapiCapture* wasapi_capture_{nullptr};     // WASAPI 环回采集器
    OpusAudioEncoder* opus_encoder_{nullptr};    // Opus 编码器
    AudioSender* audio_sender_{nullptr};         // UDP 音频发送器

    std::vector<int16_t> audio_pcm_buffer_;     // PCM 累积缓冲区（凑帧用）
    uint16_t audio_frame_index_{0};              // 音频帧序号
    uint32_t audio_timestamp_ms_{0};             // 音频时间戳（毫秒）

    void OnAudioData(const int16_t* pcm_data, int sample_count, uint32_t timestamp_ms);
};
```

### Init 中的音频初始化（第九步）

```
第九步：初始化音频组件
  1. wasapi_capture_ = new WasapiCapture()
     wasapi_capture_->Init(48000, 2)             // 48kHz 立体声

  2. opus_encoder_ = new OpusAudioEncoder()
     opus_encoder_->Init(48000, 2, 128000, 20)  // 128kbps, 20ms 帧

  3. audio_sender_ = new AudioSender()
     audio_sender_->Init(dest_ip, audio_port)    // UDP 发送到客户端

  4. wasapi_capture_->SetCallback(OnAudioData)   // 注册回调
```

### Run 中的音频启动

```
Run:
  // ---- 启动音频采集（独立线程，不阻塞视频主循环）----
  if (wasapi_capture_)
      wasapi_capture_->Start()

  while running:
      // ---- 视频主循环（采集→编码→发送）----
      // 音频在独立线程中运行，通过回调 OnAudioData 异步处理
```

**为什么音频用独立线程**：
视频主循环按固定帧率（60fps = 16.6ms/帧）运行。WASAPI 采集回调的触发频率取决于设备缓冲区大小，通常每 3~10ms 就有一次数据。如果把音频采集放在视频主循环中，会打破帧率控制；反之，视频编码的耗时也会导致音频缓冲区溢出。独立线程让音视频管线完全解耦。

### OnAudioData 回调：凑帧 + 编码 + 发送

```
OnAudioData(pcm_data, sample_count, timestamp_ms):
  1. 追加 PCM 到缓冲区
     audio_pcm_buffer_.insert(end, pcm_data, pcm_data + sample_count × channels)

  2. 凑够一帧就编码发送
     frame_total = 960 × 2 = 1920                // Opus 帧大小 × 声道数

     while audio_pcm_buffer_.size() >= 1920:
       a. opus_encoder_->Encode(buffer.data(), 960, opus_data)
       b. audio_sender_->SendFrame(opus_data, encoded, frame_index++, timestamp)
       c. audio_timestamp_ms_ += 20               // 时间戳递增 20ms
       d. 移除已编码的 1920 个采样
```

**为什么需要凑帧**：
WASAPI 每次 `GetBuffer` 返回的采样数不固定（取决于设备缓冲区和消费速度），可能是 480、960、1440 等任意值。但 Opus 编码器要求每帧恰好 960 samples/channel（20ms）。所以需要把 WASAPI 返回的 PCM 数据先追加到缓冲区，凑够 1920 个采样（960 × 2 声道）再编码。

### DecodeLoop 重构：从单体函数到 7 个模块

原 `DecodeLoop()` 是一个 300+ 行的巨型函数，串流路径和文件路径混在一起。第四阶段拆分为 7 个职责单一的函数：

```cpp
void DecodeLoop();           // 调度器：初始化 → 等待队列 → 选路径 → 清理

void GetStreamInfo(double& fps, AVRational& video_tb,
                   bool& has_audio, double& frame_interval_ms);  // 获取流信息

void ProcessFileLoop(bool has_audio, AVRational video_tb,
                     double fps, double frame_interval_ms);     // 文件播放主循环

void CleanupFrames();                    // 清理残留帧队列
```

```
DecodeLoop 调度流程：

  CoInitializeEx(MTA)
  │
  ├─ GetStreamInfo()           // 获取帧率、时基、音频标志
  │
  ├─ WaitForFrameQueues()      // 等待视频/音频帧队列有数据
  │    └─ 返回 false → 退出
  │
  ├─ InitSyncState()           // 重置 frame_timer、丢帧计数器
  │
  ├─ 路径选择：
  │    ├─ is_streaming_ → ProcessStreamingLoop()   // 喂音频 + 渲染视频（无同步）
  │    └─ else          → ProcessFileLoop()        // 音视频同步 + 渲染
  │
  ├─ CleanupFrames()           // 清空残留帧
  │
  └─ CoUninitialize()
```

### ProcessStreamingLoop：串流主循环

```cpp
void ProcessStreamingLoop(bool has_audio, AVRational video_tb)
{
    while (playing_)
    {
        // ---- 喂音频（非阻塞，先检查空间）----
        if (has_audio)
        {
            while (stream_audio_renderer_->CanAcceptFrame() &&
                   audio_frame_queue_.TryPop(af) && n < 5)
            {
                stream_audio_renderer_->FeedFrame(af);
                av_frame_free(&af);
            }
        }

        // ---- 取视频帧（阻塞）----
        AVFrame* video_frame = video_frame_queue_.Pop();

        // ---- 延迟初始化渲染器（首帧分辨率）----
        if (!renderer_inited_)
            video_renderer_->Init(device, frame->width, frame->height);

        // ---- 立刻渲染，不做同步 ----
        video_renderer_->Render(video_frame);
        av_frame_free(&video_frame);
    }
}
```

**与文件模式的区别**：

| 对比项 | ProcessStreamingLoop | ProcessFileLoop |
|--------|---------------------|-----------------|
| 音频渲染器 | stream_audio_renderer_ (WASAPI) | audio_renderer_ (QAudioOutput) |
| 音视频同步 | 无（收到帧立刻渲染） | 有（音频主时钟 + frame_timer） |
| 丢帧策略 | 不丢帧 | 早期丢帧 + 晚期丢帧 |
| 帧等待 | Pop() 阻塞等待 | sleep_to(target_ms) 精确等待 |

## 技术决策说明

### 1. 为什么用 WASAPI Loopback 而不是立体声混音

**为什么是这个方案**：
立体声混音依赖声卡驱动支持，很多笔记本和 USB 音频设备没有此功能。WASAPI Loopback 是 Windows Vista+ 的系统级 API，只要系统有音频设备就能用，不依赖驱动特性。

**底层是什么**：
WASAPI 共享模式下，所有应用的音频流经过 Windows 音频引擎混音后送往渲染端点（扬声器）。`AUDCLNT_STREAMFLAGS_LOOPBACK` 标志让 `IAudioCaptureClient` 挂在渲染端点上，捕获混音后的输出数据——相当于"录下声卡正在播放的声音"。

**如果是你你会怎么学**：
看 MSDN 的 "Capturing a Stream" 文档，重点理解 Loopback 模式与普通 Capture 模式的区别。注意 Loopback 必须使用 `GetMixFormat()` 返回的格式（不能自定义），因为混音引擎输出格式是固定的。

### 2. 为什么用 Opus 而不是 AAC

**为什么是这个方案**：
AAC 的编码延迟通常在 50ms 以上（需要 1024 个采样 = 21.3ms @ 48kHz，加上编码器内部缓冲）。Opus 支持 2.5~60ms 的帧大小，20ms 帧只需 960 个采样，端到端编码延迟 < 5ms。Moonlight 官方也使用 Opus。

**底层是什么**：
Opus 结合了 SILK（语音）和 CELT（音乐）两套编解码器，内部根据信号特征自动切换。`OPUS_APPLICATION_AUDIO` 告诉编码器优先保真音乐信号而非语音优化。Opus 的延迟主要来自帧大小（20ms），编码计算本身在微秒级。

**如果是你你会怎么学**：
看 Opus 官方网站的交互式演示（opus-codec.org），对比不同码率下 Opus 和 AAC 的音质。读 RFC 6716 了解 Opus 的内部结构（SILK + CELT 双模式）。

### 3. 为什么串流用 WASAPI 渲染而不是 QAudioOutput

**为什么是这个方案**：
Qt 5.14 的 QAudioOutput 在 Release 模式下设备枚举失败（"using null output device"），导致串流模式无声音。直接用 WASAPI 的 `IAudioRenderClient` 绕过 Qt 的设备管理层，COM 对象在子线程中创建，时序可控。

**底层是什么**：
QAudioOutput 内部也是调用 WASAPI，但它通过 `QAudioDeviceInfo::availableDevices()` 枚举设备，这步依赖 Qt 的插件系统在主线程中初始化 COM。如果 Qt 的插件加载时机晚于音频模块初始化，设备列表为空。直接用 `CoCreateInstance(MMDeviceEnumerator)` 不依赖 Qt 插件，在任何线程中都能正常工作。

**如果是你你会怎么学**：
看 Qt 源码 `qaudiodeviceinfo_win32.cpp` 中 `availableDevices()` 的实现，对比直接调用 `IMMDeviceEnumerator::EnumAudioEndpoints` 的路径。理解 Qt 插件系统的加载时序问题。

### 4. 为什么 WASAPI 缓冲区设 40ms

**为什么是这个方案**：
Opus 每帧 20ms，WASAPI 缓冲区必须能容纳至少 2 帧。如果缓冲区只有 10ms（WASAPI 默认），一帧 20ms 的 PCM 数据放不进去，会导致 buffer underflow——声卡消费完了缓冲区但新数据还没写入，播放未初始化的内存，产生刺耳杂音。

**底层是什么**：
WASAPI 共享模式下，声卡以硬件采样率持续消费缓冲区。`GetCurrentPadding` 返回当前缓冲区中已填充但尚未播放的帧数。如果 `padding` 降到 0，声卡会播放静音或残留数据。40ms 缓冲区（1920 帧）给编解码和网络抖动留了 2 帧的余量。

**如果是你你会怎么学**：
看 MSDN "Rendering a Stream" 文档中关于 buffer management 的部分。用 `GetCurrentPadding` 打印 padding 随时间的变化曲线，观察缓冲区水位波动。

### 5. 为什么把音频渲染拆成两个类

**为什么是这个方案**：
文件播放用 QAudioOutput（Debug/Release 都正常，且需要 Qt 的音量控制），串流播放用 WASAPI（绕过 Qt 的设备枚举问题）。两者的初始化流程、缓冲区管理、音量控制完全不同，强行继承会产生大量条件分支。两个独立类各管各的，`FFmpegPlayer` 通过 `is_streaming_` 标志选择使用哪个。

**底层是什么**：
`AudioRenderer` 封装 `QAudioOutput`，内部是 Qt 的音频插件系统；`StreamAudioRenderer` 封装 `IAudioRenderClient`，直接操作 WASAPI COM 对象。两者的共同接口是 `CanAcceptFrame()` + `FeedFrame()`，但实现完全不同——前者通过 Qt 信号槽投递数据，后者直接 `GetBuffer`/`ReleaseBuffer` 写硬件缓冲区。

**如果是你你会怎么学**：
对比 Qt 的 `QAudioOutput` 源码和 WASAPI 的 `IAudioRenderClient` 文档。理解"抽象层"什么时候是好处（简化 API）什么时候是负担（隐藏了关键细节导致调试困难）。

## 踩过的坑

### 坑 1：WASAPI Loopback 收不到数据

**现象**：`GetNextPacketSize` 永远返回 0，采集线程一直空转。

**原因**：WASAPI loopback 依赖音频引擎的混音输出。当系统没有声音播放时，音频引擎处于空闲状态，不产生数据包。

**修复**：创建一个辅助渲染流（`IAudioClient` 不加 `LOOPBACK` 标志），启动但不写入数据。这让音频引擎保持活跃，loopback 就能持续收到数据包（包括静音包）。

### 坑 2：Release 模式 QAudioOutput 无声音

**现象**：Debug 模式串流音频正常，Release 模式日志显示 "using null output device"，无声音。

**原因**：Qt 5.14 的 QAudioOutput 在 Release 模式下设备枚举失败。`QAudioDeviceInfo::availableDevices()` 返回空列表，`QAudioOutput` 使用了 null 设备。

**修复**：新建 `StreamAudioRenderer` 类，直接用 WASAPI 的 `IAudioRenderClient` 替代 QAudioOutput。COM 对象在 `FFmpegPlayer::Play()` 启动的子线程中创建，COM 初始化时序可控。

### 坑 3：WASAPI 缓冲区 underflow 导致刺耳杂音

**现象**：串流音频有周期性的刺耳杂音，类似"嘟嘟"声。

**原因**：WASAPI 缓冲区默认 10ms，但 Opus 每帧 20ms。一帧 20ms 的 PCM 数据写入 10ms 的缓冲区时放不下，声卡在等待数据期间播放了未初始化的内存。

**修复**：
1. 将 WASAPI 缓冲区增大到 40ms（`REFERENCE_TIME = 400000`，即 40ms = 1920 帧 @ 48kHz）
2. 启动时预填充整个缓冲区为静音（`memset(0)`），防止播放残留数据

### 坑 4：文件模式 sleep 导致串流音频断续

**现象**：文件播放模式下，串流音频出现周期性的"嘟嘟"杂音。

**原因**：`ProcessFileLoop` 的音视频同步使用 `sleep_for(33~133ms)` 等待下一帧显示时间。sleep 期间 `ProcessStreamingLoop` 不执行，音频帧堆积在队列中没人消费，WASAPI 缓冲区被耗尽。

**修复**：将 `ProcessFileLoop` 中的单次长 `sleep_for` 替换为分段短睡 + 持续喂音频的忙等循环：
```
// 原来一次性睡 33ms，音频缓冲区 underflow
sleep_for(33ms)

// 改为每 5ms 醒来喂一次音频，保持缓冲区水位
while (remaining > 0) {
    feed_audio();           // 喂音频
    sleep_for(5ms);         // 短睡
    remaining -= 5;
}
```

### 坑 5：CanAcceptFrame 首帧阻塞

**现象**：串流模式启动后音频队列堆积，`CanAcceptFrame` 一直返回 false。

**原因**：`frame_bytes_` 初始值为 0，`CanAcceptFrame` 检查 `free_bytes >= frame_bytes_` 即 `free_bytes >= 0`，逻辑上应该为 true。但实际 `frame_bytes_` 在 `FeedFrame` 首次调用时才计算，首帧前为 0 导致比较结果不确定。

**修复**：首帧特殊处理——`frame_bytes_ == 0` 时不检查帧大小，只要缓冲区有空闲就接受：
```cpp
if (frame_bytes_ == 0)
    return free_bytes > 0;
return free_bytes >= (UINT32)frame_bytes_;
```

### 坑 6：AVRational 前向声明缺失

**现象**：`DecodeLoop` 拆分后编译报 `'AVRational' identifier not found`。

**原因**：拆分后 `FFmpegPlayer.h` 中新增了使用 `AVRational` 参数的函数声明，但头文件中只有 `AVPacket` 和 `AVFrame` 的前向声明，没有 `AVRational`。

**修复**：在 `FFmpegPlayer.h` 中添加前向声明：
```cpp
struct AVPacket;
struct AVFrame;
struct AVRational;          // 新增
```
