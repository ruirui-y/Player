# 第八阶段：体验打磨 — 详细实现设计

> 基于代码探索分析的精确方案。当前渲染管线、色彩空间、OSD、输入的现状和缺口都已明确。

## 1. 现状分析

### 1.1 渲染管线现状

```
FFmpegPlayer::ProcessStreamingLoop()
  └→ video_frame_queue_.Pop()       // 阻塞等帧
  └→ video_renderer_->Render()      // "来一帧渲一帧"
       └→ D3D11Pipeline::Execute()
            └→ swapchain_->Present(1, 0)  // 唯一的 VSync，阻塞到垂直空白
```

**问题**：帧率不稳（50-70fps 波动）时，有时一帧等不到 VSync 就 loop，有时一帧跨两个 VSync。画面感知上有「抖动」——不是撕裂（`Present(1,0)` 已经防撕裂了），而是帧间隔不均匀。

**根因**：没有独立的 VSync 时钟驱动渲染节奏。解码出来的帧不按显示节奏走，全看解码速度和队列深浅。

### 1.2 色彩空间现状

```
服务端采集 → BGRA GPU 纹理 → NVENC 编码(BT.709 full) → H.264 → 
客户端解码 → NV12 纹理 → HLSL CSC (BT.709 limited→full) → B8G8R8A8 交换链
```

**问题**：
- CSC 矩阵硬编码 BT.709，BT.601/2020 一律走错
- 不支持 HDR（交换链格式 B8G8R8A8 是 8bit SDR）
- 服务端不传色彩空间元数据给客户端

**根因**：HLSL 着色器只有一套矩阵；编码器的 `color_range/colorspace` 写死；`CaptureFrame` 没有色彩字段。

### 1.3 OSD 现状

StreamWindow 底部有个 QLabel 状态栏显示连接状态文字。串流画面上没有任何 FPS/RTT/丢包率叠加。

### 1.4 输入现状

键盘（WH_KEYBOARD_LL）+ 鼠标（Raw Input）齐全。没有手柄、触屏、震动支持。

## 3. 帧步调 Pacer（8.1）

### 3.1 原理

```
当前（无 Pacer）：
  解码帧到达时间:  |  |   |    |  |   |
  VSync 信号：     |  |  |  |  |  |  |  |
  实际 Present：   |  |  |  |  |  |  |  |    ← 帧间隔不均匀

加入 Pacer 后：
  解码帧 → 入 pacing 队列
  VSync 线程 → 等 VSync → 从队列取最近一帧 → Present
                    → 队列深度 > 2 → 丢最旧帧
                    → 队列为空 → 重复上一帧
  Present：        |  |  |  |  |  |  |  |    ← 帧间隔均匀
```

### 3.2 需要什么

```
┌─────────────────────────────────────┐
│ FFmpegPlayer::DecodeLoop (主线)      │
│                                     │
│  解码出帧 → pacing_queue_.Push()    │
│                                     │
│  如果 pacing_queue_ 满 → 丢最旧帧    │
└──────────────┬──────────────────────┘
               │
               ▼
┌─────────────────────────────────────┐
│ VSync 线程（独立线程，高优先级）      │
│                                     │
│  while (playing) {                  │
│    D3DKMTWaitForVerticalBlankEvent()│  ← 内核态阻塞，1μs 精度
│    frame = pacing_queue_.Pop(0)     │  ← 非阻塞取最新帧
│    如果有新帧 → Present()           │
│    没有 → 重复上一帧的 Present()    │
│  }                                 │
└─────────────────────────────────────┘
```

### 3.3 代码改动

**新增文件**：`Client/Core/Pacer.h/.cpp`

```cpp
class Pacer
{
public:
    void Start(HWND output_window, int refresh_rate);
    void Stop();

    // 解码线程调用：推入一帧（如果满了自动丢最旧的）
    void PushFrame(AVFrame* frame);

    // 获取统计
    int GetPacingQueueDepth() const;
    int GetRenderFps() const;

private:
    void VsyncLoop();

    SafeQueue<AVFrame*> pacing_queue_;  // 上限 3 帧
    std::thread vsync_thread_;
    std::atomic<bool> running_{false};
    int refresh_rate_{60};
    uint64_t last_vsync_time_{0};
};
```

**改动量估**：~200 行新代码，FFmpegPlayer 中改 ~10 行（Render → PushFrame）。

**注意事项**：
- `D3DKMTWaitForVerticalBlankEvent` 需要 `#include <d3dkmthk.h>` 链接 `gdi32.lib`
- VSync 线程需要设备上下文，可与渲染器共享 D3D11 的 `ID3D11DeviceContext`
- 首次启动需要 wait 一次对齐到下一个 VSync

## 4. OSD 统计叠加（8.3）

### 4.1 方案选择

| 方案 | 复杂度 | 效果 |
|------|--------|------|
| QLabel 浮层（Qt 控件覆盖在视频上） | 低 | 简单但无法嵌入 D3D11 渲染管线，可能影响性能 |
| D2D 覆盖（在 SwapChain 上叠加）| 中 | 可以，但引入 D2D 依赖，和 D3D11 混合使用有坑 |
| 扩展 StreamWindow 状态栏 | **最低** | 复用现有状态栏，多显示几行数据即可 |

**决策：用方案 3——扩展现有状态栏**。

理由：P0 目标是「测试时能看到实时数据」，不需要漂亮覆盖层。StreamWindow 底部已经有 24px 状态栏，扩展成两行或横向排列即可。以后可以升级成 D3D11 HUD。

### 4.2 状态栏格式

```
┌─────────────────────────────────────────────────────────┐
│  已连接 — 控制信道就绪   │ FPS:58 │ RTT:12ms │ 丢包:0.5% │
└─────────────────────────────────────────────────────────┘
```

### 4.3 数据来源

| 指标 | 来源 | 更新频率 |
|------|------|---------|
| 连接状态 | `StreamWindow::SetStatusText` | 事件驱动 |
| 接收 FPS | `VideoReceiver::GetStats()`（已有） | 每秒 |
| RTT | `RttMeasurer::GetLatestRtt()`（已有） | 实时 |
| 丢包率 | `VideoReceiver::GetStats()`（已有） | 每秒 |
| 解码 FPS | Pacer（新增） | 每秒 |

### 4.4 代码改动

`StreamWindow` 新增定时器，每秒从 `VideoReceiver` / `RttMeasurer` 读取统计并更新状态栏文字。改动量 ~30 行。

**需要在 FFmpegPlayer 暴露更多读取接口**：
```cpp
// FFmpegPlayer 新增
int GetReceiveFps() const;
int GetRtt() const;
float GetLossRate() const;
```

## 5. 不走的内容（留后续）

### 色彩空间（8.2）

不动，原因：
- 当前 SDR 显示器上 BT.709 是正确的
- HDR 需要：服务端传 DXGI HDR 元数据 + 编码器输出 10bit + 交换链格式改 P010 → 链条长
- 小团队先不碰 HDR

### 手柄输入（8.4）

不动，原因：
- XInput 客户端采集 ~50 行，ViGEm 服务端注入 ~100 行
- 但 ViGEm 是独立驱动安装（`ViGEmBus`），分发和部署复杂
- 手柄串流是低频需求，不急着做

## 8. 验收标准

| 场景 | 预期行为 |
|------|---------|
| 60fps 源 + 60Hz 显示器 | 帧间隔均匀，无抖动感 |
| 30fps 源 + 60Hz 显示器 | 每帧显示两次，不等间隔但是重复帧无抖动 |
| 丢包导致帧延迟 | Pacer 丢旧帧保持节奏，不积压 |
| 状态栏 OSD | 每秒刷新 FPS/RTT/丢包率 |
| CPU/GPU 开销 | Pacer 线程 CPU < 1%，几乎零 |

## 9. 实测记录（2026-08-01）

### 测试流程

```
1. 编译 → 服务端启动 → 客户端连接 → 观察画面顺滑度
2. OSD 状态栏验证（接收FPS / 渲染FPS / RTT）
3. 全屏跨屏测试（全屏状态 + Win+Shift+箭头 → 点全屏按钮）
4. 长时间运行（>10分钟）→ 鼠标键盘响应检查
5. 任务管理器场景（高权限窗口交互）
```

### 发现与修复

| # | 问题 | 根因 | 修复 |
|---|------|------|------|
| 1 | 画面比之前清晰 | 早期 Pacer 试了双重 VSync（WaitForVsync + Present(1,0)），导致 30fps 抖动 | Pacer 退化为纯帧计数器，VSync 全靠 Present(1,0) |
| 2 | 鼠标响应丢失 | WaitForVsync 阻塞渲染线程，间接影响输入处理 | 删除 WaitForVsync，OnFramePresented 只计数 |
| 3 | 全屏跨屏后无法退出 | `windowHandle()->screen()` 跨屏后是缓存旧值 | 进全屏时存 `fullscreen_screen_name_`，退出时比对鼠标所在屏 |
| 4 | 全屏反弹不生效 | `setScreen()` 在 `showNormal()` 后不及时 | 改用 `move()` 手动搬到目标屏中心 + `processEvents()` |
| 5 | 长时间运行后键鼠失效 | 控制信道 TCP 长连接无声断开 | 客户端+服务端双双加 TCP KeepAlive（10s 空闲 / 1s 间隔 / 3 次） |
| 6 | 任务管理器拖不动 | Windows 安全机制：高完整性级别窗口拒绝低权限进程的消息 | 非 Bug，操作系统保护 |
| 7 | 点任务管理器后输入全失效 | `SendInput` 注入高权限窗口后状态卡死 | 暂无完美修复，重启程序恢复 |

### 架构变更

Pacer 从最初的「独立 VSync 线程 + Pacing 队列」简化为「帧计数器」：

```
原设计: 独立 VSync 线程 + Pacing 队列(3帧) + D3DKMTWaitForVerticalBlankEvent
实际落地: OnFramePresented() 帧计数（每秒统计 FPS 供 OSD 用）
放弃原因: Present(1,0) 已提供 VSync，双重等待导致线程阻塞和帧率减半
```
