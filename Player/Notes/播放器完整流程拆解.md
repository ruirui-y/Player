## 整合版：从解码到渲染的完整链路

### 整体对照图

```
解码阶段 ───────────────────────────────→  渲染阶段 ──────────────────────→

文件 → [解封装] → [解码] → [GPU拷贝] → [着色器转换] → [Present上屏]
        Core/         Core/       Core/         Core/           Core/
        FFmpegDecoder FFmpegDecoder Nv12GpuUploader D3D11Pipeline  D3D11Pipeline
        ::ReadFrame   ::ReadFrame   ::UploadFrame   ::Execute      ::Execute
```

### 阶段一：图片从哪来？

FFmpeg 打开视频文件，调用硬解解码器（D3D11VA），每调用一次 `ReadFrame` 就解出一帧。

| 位置       | 细节                                                         |
| :--------- | :----------------------------------------------------------- |
| **文件**   | `Core/FFmpegDecoder.cpp`                                     |
| **函数**   | `FFmpegDecoder::ReadFrame(AVFrame* frame)`                   |
| **做的事** | 把 H.264/H.265 压缩包 → 解码成一张完整的 NV12 图像           |
| **输出**   | `AVFrame`，格式为 `AV_PIX_FMT_D3D11`（硬解）或 `AV_PIX_FMT_YUV420P`（软解） |

#### ReadFrame 内部的三阶段流程

**先理解新 API 的设计思想：** 投原料（`send_packet`）和收成品（`receive_frame`）是解耦的，比例不是 1:1。一个 I B B P 的 GOP 可能投 4 个包才收出第 1 帧（因为 B 帧依赖后面的 P 帧）。

```
ReadFrame 进入
    │
    ├─ 第①步：先试收帧
    │  avcodec_receive_frame(ctx, frame)
    │  → 解码器内部可能有缓存帧（B 帧重排序等）
    │  → 成功则直接 return 0（不用读包）
    │
    ├─ 第②步：EAGAIN → 读包 + 喂解码器
    │  while (ret == EAGAIN)          ← "不够，再喂点"
    │  {
    │      av_read_frame(fmt, pkt)        ← 从 MP4 文件里读一个压缩包
    │      │
    │      ├─ 是视频包 → avcodec_send_packet(ctx, pkt)  ← 同步入队
    │      │               │
    │      │               ├─ 返回 0      ← 包已塞入解码器内部队列
    │      │               └─ 返回 EAGAIN ← 队列满了，包没塞进去
    │      │               ↓
    │      │       avcodec_receive_frame(ctx, frame)
    │      │       → ==0 则 return 0（成功收帧）
    │      │       → EAGAIN 继续读下一个包
    │      │
    │      └─ 非视频包（音频/字幕）→ 丢弃，继续
    │  }
    │
    └─ 第③步：Flush 收尾（文件读完了）
       avcodec_send_packet(ctx, nullptr)  ← flush 命令
       while (true)
       {
           ret = avcodec_receive_frame(ctx, frame)
           → ==0 则 return 0（吐出缓存帧）
           → 否则 return AVERROR_EOF（全部解完）
       }
```

#### 异步解码的本质

**你的 DecodeLoop 看起来是同步的——"收一帧 → 渲染一帧 → 再收一帧"。但实际上 GPU 后台可能有多个帧同时在解码。**

```
时间轴 →
                              GPU 硬件解码器
                              │
CPU 线程（DecodeLoop）         │
│                              │
├─ send_packet(帧1) ──────────┤──► 同步：包塞入队列 ✅
│  receive_frame → EAGAIN     │  GPU 正在解帧1（还没解完）
│                              │
├─ send_packet(帧2) ──────────┤──► 同步：包塞入队列 ✅
│  receive_frame → EAGAIN     │  GPU 同时解帧1和帧2
│                              │
├─ receive_frame → OK! 帧1    │  ← 帧1先解完了！
└─ Render(帧1)                 │
```

**三个关键事实：**

| 事实                         | 说明                                                         |
| :--------------------------- | :----------------------------------------------------------- |
| **send_packet 是同步入队**   | 把压缩包拷贝到解码器内部的 CPU 队列里，塞进去就返回。返回值只代表"塞没塞进去"，不代表"解没解完" |
| **GPU 异步消费队列**         | GPU 从队列里取包去解码，这个过程不阻塞 CPU 线程              |
| **receive_frame 是同步收帧** | 从"已解完"队列里取一帧，有就给你，没有就 EAGAIN              |

**你的 while 循环本质上就是在做"一边喂、一边收、谁先解完拿谁"。**

```
send(帧1) → 收不到 → send(帧2) → 收不到 → send(帧3) → 收到了！（可能是帧1）
```

发送顺序和完成顺序不一定一致，因为 GPU 同时在处理多帧。这就是异步的本质。

#### 为什么需要 surface pool（纹理池）

因为有异步，所以 GPU 那边可能同时有几帧在解码流水线上。如果只有 1 张纹理：

```
send_packet(帧1) → GPU 往纹理 A 写
send_packet(帧2) → GPU 也往纹理 A 写 → 帧1 的数据被覆盖了 ❌
```

所以需要一个池子，每次 `send_packet` 时从池子里取一个空闲的抽屉让 GPU 写：

```
send_packet(帧1) → pool[0] 被 GPU 写 ← 空闲抽屉
send_packet(帧2) → pool[1] 被 GPU 写 ← 另一个空闲抽屉
send_packet(帧3) → pool[2] 被 GPU 写
receive_frame    → pool[0] 写完了！返回 AVFrame 指向 pool[0]
send_packet(帧4) → pool[0] 空闲了，可以给帧4 用
```

**pool 是 GPU 异步解码的必要基础设施。**

#### 解码后的帧在哪里？

解出来的帧在哪？**取决于解码模式：**

| 解码模式     | 帧的位置                                                     | frame->format            |
| :----------- | :----------------------------------------------------------- | :----------------------- |
| D3D11VA 硬解 | **GPU 显存**中的 `ID3D11Texture2D`（pool 里的某个抽屉），格式是 NV12 | `AV_PIX_FMT_D3D11` (170) |
| 软件解码     | **CPU 内存**中的 `data[0]`=Y, `data[1]`=UV                   | `AV_PIX_FMT_YUV420P` 等  |

**硬解情况下 AVFrame 的数据布局：**

```
AVFrame                        ID3D11Texture2D (ArraySize=20)
┌───────────────────┐          ┌────┬────┬────┬────┬────┬────┐
│ format: D3D11     │          │  0 │  1 │  2 │  3 │  4 │... │
│ data[0] ──────────┼──────────►   （直接存 ID3D11Texture2D*）
│ data[1] ──────────┼──────────►   帧在数组中的索引 (intptr_t)
│                   │          │    │    │    │ 这 │    │    │
│ pts / width /     │          │    │    │    │ 里 │    │    │
│ height ...        │          └────┴────┴────┴────┴────┴────┘
└───────────────────┘
```

**注意：** `frame->data[0]` 不是 CPU 内存指针，也不是某个结构体——它直接存的 `ID3D11Texture2D*`。之前踩过坑，错误地把它强转成了 `AVD3D11FrameDescriptor*`，读取到垃圾指针导致崩溃。正确的取法就是直接强转。

NV12 的结构：
- **Y 平面**：宽×高，每个像素 1 字节，存亮度
- **UV 平面**：宽/2 × 高/2，每两个字节存一组 UV，存颜色

### 阶段二：渲染入口 — 分派到不同渲染路径

| 位置       | 细节                                          |
| :--------- | :-------------------------------------------- |
| **文件**   | `Core/FFmpegPlayer.cpp`                       |
| **函数**   | `FFmpegPlayer::DecodeLoop()` 的渲染分支       |
| **做的事** | 根据帧格式和渲染管线状态，判断走 GPU 还是 CPU |

```
DecodeLoop 的渲染分支逻辑：
    │
    ├─ 帧是 AV_PIX_FMT_D3D11 AND D3D11Pipeline 就绪
    │  → Nv12GpuUploader::UploadFrame → D3D11Pipeline::Execute
    │    ↑ 全 GPU 管线
    │
    └─ 其他情况（硬解帧但管线未就绪、软解帧等）
       → av_hwframe_transfer_data → SoftwareRenderer::Render
         ↑ CPU 软解回退
```

**项目结构经过拆分后，渲染相关的职责分布：**

| 类                   | 是否 QObject | 职责                            | 核心接口                                    |
| :------------------- | :----------- | :------------------------------ | :------------------------------------------ |
| **D3D11Pipeline**    | ❌            | 交换链 + 着色器 + Draw/Present  | `CreateSwapChain()`、`Execute(Y, UV, w, h)` |
| **Nv12GpuUploader**  | ❌            | GPU 内部帧拷贝 + PlaneSlice SRV | `Init()`、`UploadFrame()`                   |
| **SoftwareRenderer** | ✅            | sws_scale → QImage → 信号       | `Render()`、`SigFrameReady`                 |

`FFmpegPlayer` 作为编排层，持有这三个类并在 `DecodeLoop` 中协调调用。`VideoRenderer` 已被删除。

### 阶段三：GPU 渲染管线（策略 D — 最终方案）

**核心思路：** 解码器里的帧不能直接用，所以我们自己盖一个仓库（纹理），把数据搬过来，再贴上说明书（SRV），最后把说明书交给着色器。

整个过程分三步。

---

#### 第一步：把帧从解码器的池子里搬到自己家的仓库

解码器有一个 ArraySize=20 的纹理数组，当前帧是池子里的第 N 个抽屉。我们要把它搬到自己的 NV12 纹理里（ArraySize=1，带 SHADER_RESOURCE 权限）。

不能用 `CopyResource`，因为源是数组（ArraySize=20）目标是单张（ArraySize=1），必须用 `CopySubresourceRegion` 指定只拷贝第 N 个抽屉。

```cpp
ID3D11Texture2D* decoder_texture = (ID3D11Texture2D*)frame->data[0];
int subresource_index = (int)(intptr_t)frame->data[1];

D3D11_BOX src_box = {0, 0, 0, w, h, 1};
d3d11_ctx_->CopySubresourceRegion(
    nv12_texture_, 0, 0, 0, 0,
    decoder_texture, subresource_index, &src_box);
```

搬完后的状态：

```
解码器的池子（ArraySize=20）：        自建 NV12 纹理（ArraySize=1）：
┌────┬────┬────┬────┬────┬────┐        ┌──────────────────────┐
│  0 │  1 │  2 │  3 │ ...│ 19 │ ────→  │     一帧 NV12 数据   │
└────┴────┴────┴────┴────┴────┘        └──────────────────────┘
  ↑                                    CopySubresourceRegion
  第 N 帧从池子里搬过来                  （GPU 内部，不经过 CPU）
```

**注意：这一步全程在 GPU 内部完成，CPU 不参与。** 耗时 ~0.0ms。对比旧方案（CPU 中转）的 ~4ms，这是质变。

---

#### 第二步：给仓库贴两张说明书（SRV）

自建的 `nv12_texture_` 是一张 NV12 纹理，Y 和 UV 在同一块数据里。但着色器需要把它们当成两张独立的纹理来读。解决方案：创建两个 SRV，指向同一张纹理，但用不同的 `PlaneSlice` 区分 Y 和 UV。

```cpp
// Y 平面说明书：PlaneSlice=0，格式 R8_UNORM
srv_desc.Format = DXGI_FORMAT_R8_UNORM;
srv_desc.Texture2DArray.PlaneSlice = 0;
d3d11_device3_->CreateShaderResourceView1(nv12_texture_, &srv_desc, &nv12_srv_y_);

// UV 平面说明书：PlaneSlice=1，格式 R8G8_UNORM
srv_desc.Format = DXGI_FORMAT_R8G8_UNORM;
srv_desc.Texture2DArray.PlaneSlice = 1;
d3d11_device3_->CreateShaderResourceView1(nv12_texture_, &srv_desc, &nv12_srv_uv_);
```

创建后的关系：

```
nv12_texture_（一张 NV12 纹理）
    │
    ├── nv12_srv_y_  → 说"格式 R8，读 plane 0"  → 读出来是 Y 亮度
    │
    └── nv12_srv_uv_ → 说"格式 R8G8，读 plane 1" → 读出来是 UV 色度
```

**SRV 不在纹理里面。** 纹理是仓库里的货，SRV 是贴在仓库门口的两张说明书。一个仓库可以贴多张说明书，从不同角度教你怎么用这个仓库。

**SRV 创建一次，之后每帧复用。分辨率变化时重建。**

---

#### 第三步：把两张说明书交给着色器

光有说明书不行，还得把它塞到 GPU 的寄存器里，着色器才能找到它。

```cpp
// 把两张 SRV 绑定到像素着色器的 t0 和 t1 槽位
ID3D11ShaderResourceView* srvs[] = { nv12_srv_y_, nv12_srv_uv_ };
d3d11_ctx_->PSSetShaderResources(0, 2, srvs);
//                   ↑    ↑
//              从槽位 t0  绑 2 个 SRV
```

绑定后 GPU 内部的状态：

```
像素着色器寄存器堆：
┌──────┐
│ t0   │ ← nv12_srv_y_   说明：格式 R8，地址指向 nv12_texture_ 的 plane 0
├──────┤
│ t1   │ ← nv12_srv_uv_  说明：格式 R8G8，地址指向 nv12_texture_ 的 plane 1
├──────┤
│ t2   │ (空)
└──────┘
```

然后启动着色器：

```cpp
d3d11_ctx_->VSSetShader(vertex_shader_, nullptr, 0);
d3d11_ctx_->PSSetShader(pixel_shader_, nullptr, 0);
```

着色器执行时，根据 HLSL 声明去寄存器槽位拿说明书，再按说明书去读纹理的显存：

```hlsl
Texture2D texY : register(t0);    // → 去 t0 拿 SRV → 格式 R8 → 读 Y
Texture2D texUV : register(t1);   // → 去 t1 拿 SRV → 格式 R8G8 → 读 UV

float y = texY.Sample(...).r;
float2 uv = texUV.Sample(...).rg;
```

---

#### 完整数据流

```
解码器池子[第 N 帧]（NV12，无 SRV）
    │
    ▼  CopySubresourceRegion（GPU 内部）
自建 NV12 纹理（有 SHADER_RESOURCE）
    │
    ├── nv12_srv_y_  (PlaneSlice=0, R8)   ──→  bind to t0
    └── nv12_srv_uv_ (PlaneSlice=1, R8G8)  ──→  bind to t1
                                                   │
                                                   ▼
                                          着色器采样 → NV12→RGB → Present
```

**CPU 参与度为 0%。** 旧方案（GPU→CPU 下载 + CPU→GPU 上传）的 ~4ms 开销被完全消除。

---

#### 对比旧方案

| 对比项   | 旧方案（CPU 中转）                        | 当前方案（GPU 内部）           |
| :------- | :---------------------------------------- | :----------------------------- |
| 数据流   | GPU→CPU 下载 → CPU 拆 NV12 → CPU→GPU 上传 | GPU 内部 CopySubresourceRegion |
| 额外耗时 | ~4ms                                      | ~0.0ms                         |
| CPU 参与 | 大量 memcpy                               | 0%                             |
| 纹理数量 | 3 张（1 解码 + 2 staging）                | 2 张（1 解码 + 1 自建 NV12）   |

### 阶段四：从 NV12 创建 SRV 的试错记录（四种策略）

**核心问题：** FFmpeg 硬解输出的帧在 GPU 显存里，格式是 NV12。要让它能被着色器读取，需要为它创建 SRV。这条路被两个硬约束卡住了。

#### 约束一：FFmpeg 的纹理没有 SHADER_RESOURCE 权限

FFmpeg 内部创建 D3D11VA 纹理池时：

```cpp
desc.BindFlags = D3D11_BIND_DECODER;   // 只有解码权限
// 没有 D3D11_BIND_SHADER_RESOURCE
```

D3D11 的资源属性在创建后不可修改。所以无法直接给 FFmpeg 的纹理创建 SRV。

#### 约束二：NV12 格式创建 SRV 本身就有限制

即使自己创建一个带 SHADER_RESOURCE 的 NV12 纹理，`CreateShaderResourceView` 依然返回 E_INVALIDARG。D3D11 Debug Layer 输出的错误信息是：

```
For the video format NV12, when making a D3D view, the format name for the view can't be NV12.
```

给 NV12 纹理创建 SRV 时，view 的 `Format` 字段不能写 `DXGI_FORMAT_NV12`，必须换成单通道/双通道格式，配合 `PlaneSlice` 字段来指定读的是 Y plane 还是 UV plane。而 `PlaneSlice` 在 D3D 11.1+ 的 `D3D11_TEX2D_ARRAY_SRV1` 结构体中才存在，需要通过 `ID3D11Device3::CreateShaderResourceView1` 来使用。

#### 四种策略的完整记录

| 策略  | 做法                                               | 结果                                  | 关键日志                                            |
| :---- | :------------------------------------------------- | :------------------------------------ | :-------------------------------------------------- |
| **A** | GPU→CPU 下载 → memcpy 到 R8/R8G8 纹理 → 创建 SRV   | ✅ 稳，但每帧 ~4ms 开销                | —                                                   |
| **B** | 直接取 FFmpeg 纹理创建 SRV                         | ❌ BindFlags 无 SHADER_RESOURCE        | `ArraySize=20, BindFlags=0x200`                     |
| **C** | CopyResource 到自建 NV12 纹理 → 创建 SRV           | ❌ ArraySize 不匹配 + SRV E_INVALIDARG | `CopyResource 完成 \| 创建 SRV 失败, HR=0x80070057` |
| **D** | CopySubresourceRegion + PlaneSlice SRV（D3D 11.3） | ✅ **最终方案，0.0ms**                 | `CopySubresourceRegion ✅ (帧索引=19)`               |

##### 策略 A — 最初方案（已淘汰）

```
GPU 解码纹理（NV12）
    ↓ av_hwframe_transfer_data（GPU→CPU 下载）
CPU 内存（Y=data[0], UV=data[1]）
    ↓ Map + memcpy 逐行
GPU 自己的 R8 + R8G8 纹理
    ↓ 创建两个 SRV ✅
着色器渲染
```

**为什么选拆成 R8 + R8G8？** 因为当时不知道 PlaneSlice 的存在。R8 和 R8G8 是所有显卡都支持的标准格式，没有任何创建约束，100% 成功。代价是需要 CPU 中转搬运。

##### 策略 B — 直接取 FFmpeg 纹理创建 SRV（试错）

第一次尝试时，错误地把 `frame->data[0]` 强转成了 `AVD3D11FrameDescriptor*`：

```cpp
// ❌ 错误做法——崩溃
AVD3D11FrameDescriptor* desc = (AVD3D11FrameDescriptor*)frame->data[0];
ID3D11Texture2D* tex = desc->texture;  // 读到垃圾指针
```

**教训：** 在默认 FFmpeg D3D11VA 实现中，`data[0]` 直接存的是 `ID3D11Texture2D*`，`data[1]` 存的是 `(intptr_t)index`，不需要经过任何中间结构体。直接强转即可：

```cpp
// ✅ 正确做法
ID3D11Texture2D* decoder_texture = (ID3D11Texture2D*)frame->data[0];
int subresource_index = (int)(intptr_t)frame->data[1];
```

即使取到了纹理，也因为 BindFlags 缺少 SHADER_RESOURCE，SRV 创建必然失败。这条路由一开始就走不通。

##### 策略 C — CopyResource 到自建 NV12 纹理（试错）

既然 FFmpeg 的纹理改不了权限，那就自己创建一个带 SHADER_RESOURCE 的 NV12 纹理，用 CopyResource 在 GPU 内部拷数据。

CopyResource 这一步触发了 Debug Layer 报错：

```
Cannot invoke CopyResource when the source and destination are not the same Resource type.
Src: ArraySize=20, Dst: ArraySize=1
```

源是 ArraySize=20 的数组纹理，目标是 ArraySize=1 的单张纹理，CopyResource 要求完全一致的资源类型。这条路由也走不通。需要改用 `CopySubresourceRegion`。

##### 策略 D — CopySubresourceRegion + PlaneSlice（最终方案）

结合前两个教训，最终方案用 `CopySubresourceRegion`（只拷贝数组中的某一帧到自己的单张纹理），然后通过 D3D 11.3 的 `PlaneSlice` 为 NV12 纹理创建两个 SRV（分别指向 Y 和 UV plane）。

**打通的关键线索来自 Debug Layer：** 策略 C 的 SRV 失败信息明确说了"Format 不能是 NV12"，这让人去查 MSDN 文档，发现了 `PlaneSlice` 的存在。然后确认 `PlaneSlice` 在 `d3d11_3.h` 中的 `D3D11_TEX2D_ARRAY_SRV1` 结构体里，通过 `ID3D11Device3` 接口访问。

**验证成功的日志：**

```
[UploadStrategy] "D: CopySubresourceRegion → PlaneSlice SRV" 成功 | "创建 NV12 纹理 + PlaneSlice SRV ✅ | CopySubresourceRegion ✅ (帧索引=19)" "| 耗时 0.7ms"
```

#### 三条路全部走完的证据

| 尝试                                                         | 结果                                  | 结论                                      |
| :----------------------------------------------------------- | :------------------------------------ | :---------------------------------------- |
| 直接给 FFmpeg 的 NV12 纹理创建 SRV                           | ❌ BindFlags 没有 SHADER_RESOURCE      | FFmpeg 的纹理无法修改                     |

```
GPU 解码 → CopySubresourceRegion（GPU 内部）→ PlaneSlice SRV → 着色器 NV12→RGB → Present
```

CPU 参与度为 0%。之前 4ms 的 GPU→CPU→GPU 中转开销被完全消除。

### 阶段五：SRV — 对应"去哪找图片？"

| 位置       | 细节                                                 |
| :--------- | :--------------------------------------------------- |
| **文件**   | `Core/Nv12GpuUploader.cpp`                           |
| **函数**   | `Nv12GpuUploader::CreatePlaneSliceSRVs()`            |
| **做的事** | 为自建 NV12 纹理创建两个 SRV，分别指向 Y 和 UV plane |
| **本质**   | 给着色器一份"说明书"：纹理在哪、什么格式、几维       |

```cpp
D3D11_SHADER_RESOURCE_VIEW_DESC1 srv_desc = {};
srv_desc.ViewDimension = D3D11_SRV_DIMENSION_TEXTURE2DARRAY;
srv_desc.Texture2DArray.MipLevels = 1;
srv_desc.Texture2DArray.FirstArraySlice = 0;
srv_desc.Texture2DArray.ArraySize = 1;

// Y 平面：PlaneSlice=0, R8_UNORM
srv_desc.Format = DXGI_FORMAT_R8_UNORM;
srv_desc.Texture2DArray.PlaneSlice = 0;
d3d11_device3_->CreateShaderResourceView1(nv12_texture_, &srv_desc, &tmp_y);
nv12_srv_y_ = tmp_y;

// UV 平面：PlaneSlice=1, R8G8_UNORM
srv_desc.Format = DXGI_FORMAT_R8G8_UNORM;
srv_desc.Texture2DArray.PlaneSlice = 1;
d3d11_device3_->CreateShaderResourceView1(nv12_texture_, &srv_desc, &tmp_uv);
nv12_srv_uv_ = tmp_uv;
```

**SRV 的生命周期：** 首次 `UploadFrame` 时创建一次，之后每帧复用。分辨率变化时重建。不需要每帧创建。

### 阶段七：着色器 + Draw — 对应"怎么绘制？"

| 位置           | 细节                                                         |
| :------------- | :----------------------------------------------------------- |
| **文件**       | `Core/D3D11Pipeline.cpp`                                     |
| **函数**       | `D3D11Pipeline::Execute()`                                   |
| **着色器代码** | 内嵌在 `shader_code` 字符串中的 HLSL                         |
| **编译**       | `D3D11Pipeline::InitShaders()` — 在 CreateSwapChain 时一次编译 |

**每帧渲染时的完整调用：**

```cpp
void D3D11Pipeline::Execute(
    ID3D11ShaderResourceView* srv_y,
    ID3D11ShaderResourceView* srv_uv,
    int width, int height)
{
    // ① 绑定渲染目标（告诉 PS 把结果画到后缓冲）
    d3d11_ctx_->OMSetRenderTargets(1, &rtv_, nullptr);

    // ② 设置视口（画面在窗口里的位置和大小）
    D3D11_VIEWPORT vp = {0, 0, (float)width, (float)height, 0, 1};
    d3d11_ctx_->RSSetViewports(1, &vp);

    // ③ 装配着色器
    d3d11_ctx_->VSSetShader(vertex_shader_, nullptr, 0);
    d3d11_ctx_->PSSetShader(pixel_shader_, nullptr, 0);
    d3d11_ctx_->PSSetShaderResources(0, 2, {srv_y, srv_uv});
    d3d11_ctx_->PSSetSamplers(0, 1, &sampler_linear_);

    // ④ 画一个三角形（VS → 光栅化 → PS）
    d3d11_ctx_->Draw(3, 0);

    // ⑤ 上屏
    swapchain_->Present(1, 0);
}
```

**GPU 渲染管线在这一帧里做的事：**

```
Draw(3,0)
    │
    ├─ 顶点着色器 VS（每帧执行 3 次，对 3 个顶点）
    │   └─ 用 SV_VertexID 生成 3 个顶点的坐标 + 纹理坐标
    │      顶点0：(-1, 1)  Tex(0,0)
    │      顶点1：( 3, 1)  Tex(2,0)
    │      顶点2：(-1,-3)  Tex(0,2)
    │      → 三个顶点构成一个覆盖全屏的大三角形
    │
    ├─ 光栅化器（GPU 自动完成）
    │   └─ 算出三角形覆盖了哪些像素
    │      对每个像素：插值算出 Tex 坐标
    │
    └─ 像素着色器 PS（对屏幕上的每个像素执行一次）
        └─ 用 Tex 坐标采样两张纹理：
           texY.Sample(samLinear, tex)   → 取亮度 Y
           texUV.Sample(samLinear, tex)  → 取色度 UV
           → NV12 → RGB 转换
           → 输出 RGB 值 → 写到 RTV（后缓冲）
```

## 一个模糊的需求是怎么被拆清楚的

一开始你只有一个目标：**把视频帧用 GPU 画到屏幕上。**

你不知道该从哪下手，但你做了最对的一件事——**从两头开始追问**。

先从输入那头问：**"视频帧从哪里来？"** 摸出了 `ReadFrame` 的三阶段流程，知道了帧在 GPU 显存里，格式是 NV12。

再从输出那头问：**"GPU 怎么把帧画到屏幕上？"** 你发现"画"不是凭空生成的，它需要回答一连串的问题：

- **画到哪里？** → 需要一个窗口 → 交换链
- GPU 说"我不能直接往纹理里画" → 需要一个许可证 → **RTV**
- **怎么算每个像素的颜色？** → 需要一个程序 → **着色器**
- 着色器不是凭空算的，它是从某个地方抄数据来算的 → **"从哪里抄"**

"从哪里抄"这个追问把你带到了最核心的地方。你发现数据在 FFmpeg 的纹理池里，没有 SRV 权限，着色器读不了。试了几种办法之后，你找到了答案：自己建一个纹理把帧搬过来，再创建一个 SRV 给着色器指路。SRV 不是放在纹理里面的，你得主动把它塞进 GPU 的寄存器，着色器通过 `register(t0/t1)` 才能找到它。

每一步追问，都把模糊的概念拆成了两块——"我需要什么"和"GPU 提供了什么"，中间缺什么就补什么对象。缺窗口就建交换链，缺许可证就建 RTV，缺数据来源就建纹理 + SRV。

最后拼出来的图是这样的：

Plain Text



```
帧从哪里来 → 放在哪块显存 → 怎么搬过来
                              ↓
怎么告诉着色器去哪读 → 着色器怎么算颜色 → 算完写到哪里 → 窗口显示
```
